# A7 — Intra-SKILL protocol coherence audit (orchestrate-v2-D-workflow `SKILL.md`)

Audit target: `D:/Something/research/MATE-Automation-V4/.agents/skills/orchestrate-v2-D-workflow/SKILL.md` (78 lines, Phases 0–5 + Invariants + Cost control + Failure handling + Edge cases).

**Lens (and what is OUT of scope).** This file treats `SKILL.md` as a *standalone control-flow specification* and hunts only for (a) prose that contradicts other prose inside the same file, and (b) multi-turn phase-sequencing footguns a literal reader would walk into. It deliberately does **not** cross-check the SKILL against the engine (`orchestrate-inline.workflow.js`) — every SKILL↔ENGINE mismatch belongs to **A2** (consistency), **A4** (schema/cost), or **A6** (phantom caps), and pure engine logic belongs to **A1**. A finding is rejected here if its force depends on what the engine actually does; it survives only if the contradiction/footgun is visible from the SKILL text alone.

**Method.** Every citation quotes the literal `SKILL.md` line. The harness facts I rely on (AskUserQuestion blocks for a user answer → ends the turn; a background `Workflow` launch ends the turn and a `<task-notification>` re-invokes later) are not engine-internal — they are stated *by the SKILL itself* at L36 ("runs in the background, returns a task id, your turn ends") and L44 ("A `<task-notification>` re-invokes you on completion"), and L19/L76 treat AskUserQuestion as a "halt". So the turn-boundary reasoning below is intra-SKILL, derived from the SKILL's own stated semantics.

**Severity legend.** *contradiction* = two SKILL statements cannot both be obeyed as written; *footgun* = a literal reader is led into an unsafe or undefined sequence; *gap* = the protocol leaves a reachable state undefined; *nit* = coherence wrinkle, low harm.

## S1 — CARVE-OUT (Phase 2.5) starts a long-running job BEFORE the cost-gate confirms scope; the transparency invariant frames carve-outs as a pre-execution surface that the phase ordering defeats; the cost estimate assigns carve-outs no term. **footgun + contradiction**

**The instruction is an action, placed before the confirmation.** Phase 2.5 (SKILL:28):
> "**2.5 — CARVE-OUT.** Pull any training / build / data-conversion / long-running items OUT of the work-list and **run them yourself via `Bash run_in_background: true`, sequentially** …"

"run them yourself … `run_in_background: true`" is an *imperative to execute now* — a literal reader launches the GPU/build job at Phase 2.5. The first and only point at which the user confirms anything is the Phase-3 cost-gate, which sits two phases later (SKILL:34–35):
> "**3 — EXECUTE.** 1. **Cost-gate (⏸ confirm):** present the work-list scope … **carved-out processes**, and a rough agent estimate … `AskUserQuestion` to confirm."

So the sequence the prose dictates is **2.5 launch the carve-out → 2.75 gate → 3.1 ask the user to confirm "carved-out processes"**. By the time the user is shown the carve-out at the cost-gate, the carve-out is already running. The Invariants section reinforces the *expectation* that this is a pre-execution surface (SKILL:64):
> "**Transparency:** the GATE decision, **carve-outs**, and cost estimate are always surfaced to the user."

A reader who takes "carve-outs are always surfaced to the user" as a *gate* (decide → surface → then run) is contradicted by the Phase-2.5 ordering (run → later surface). The two readings cannot both hold: either 2.5 means "run now" (then L64's surfacing is post-hoc, not a gate) or L64 means "surface before running" (then 2.5's "run them yourself" is premature). The SKILL never reconciles them.

**Sub-point — the carve-out is uncosted at the only cost gate.** The cost-gate's estimate formula (SKILL:35) is "≈ items × 2, × up to maxRounds on contested items, + critic + finalizer" — every term is an *agent* count. Carve-outs are Bash subprocesses, not agents, so they contribute **zero** to the displayed estimate even though SKILL:67 calls the cost-gate "the primary cap" on the run's cost. The carve-out is *listed* ("carved-out processes") but never *costed* (no GPU-hours, wall-clock, or resource term). The most expensive thing the run does (a training job) is invisible to the protocol's primary cost control.

**Why intra-SKILL.** This is purely about the *order of the phases as written* (2.5 before 3.1) and the framing of an Invariant (L64) against a Phase instruction (L28/L35) — no engine behavior is involved; the engine never sees the carve-out at all (SKILL:28 says carve-outs run "never inside a workflow").

**Non-overlap.** A5 §3 (O1) only notes the carve-out branch is *untested by evals*; A5 §4 only notes the cost-gate ends the turn — neither states the run-before-confirm ordering or the uncosted-carve-out point. A6 concerns phantom *engine* caps (concurrency/budget), not the cost-gate's omission of a carve-out term. Not among the 5 evolution.md findings (which cover mode-collapse, the gate route, big-task-only, default agent type, FINALIZE). **Honest hedge:** a charitable reader could argue 2.5's "run them yourself" is meant to fire only *after* the user has implicitly blessed the plan — but the prose places no confirmation between 2.5 and the launch, and L64's "always surfaced" is the closest thing to a gate, which lands too late. The contradiction is real under the literal reading; I flag it as ordering-ambiguous rather than a guaranteed double-spend.

## S2 — Phase 3.5 → Phase 4 is an undescribed multi-turn LOOP: the escalation re-dispatch is itself a turn-ending background launch, but Phases 4 and 5 are written as the linear next steps, leaving the post-completion re-entry target undefined. **footgun**

Phase 3.5 (SKILL:46):
> "**3.5 — ESCALATE.** On completion, if `needsHuman` is non-null: surface it via `AskUserQuestion` … then **re-dispatch ONLY the escalated item(s) as a fresh scoped `Workflow`** (one or few items …) …"

A "fresh scoped `Workflow`" is the same launch primitive Phase 3 step 2 describes, and the SKILL has already told the reader what that primitive does (SKILL:36): "runs in the background, returns a task id, **your turn ends**", with completion arriving later as a `<task-notification>` (SKILL:44). Therefore the Phase-3.5 re-dispatch **ends the turn**, exactly like the Phase-3 launch. When that re-dispatched workflow later completes and re-invokes the orchestrator, the protocol gives no rule for *where execution resumes*:
- Phase 3.5 is written as a one-shot ("On completion … re-dispatch"), but the *re-dispatched* run can itself return a non-null `needsHuman`, which is the precise trigger for Phase 3.5 — i.e. there is an implicit **loop** back into 3.5.
- Phases 4 (SKILL:48) and 5 (SKILL:58) are laid out as the strictly linear continuation, with no branch saying "if the re-dispatch also escalates, return to 3.5; otherwise proceed to 4."

So a literal reader who is re-invoked after a 3.5 re-dispatch cannot tell whether to re-evaluate `needsHuman` (re-enter 3.5) or fall through to SYNTHESIZE (Phase 4). The control flow is a loop the prose renders as a straight line.

**Why intra-SKILL.** The ambiguity is in the SKILL's own phase numbering/sequencing and its own stated launch semantics (L36/L44). It does not depend on the engine's `needsHuman` shape — even granting a perfectly-shaped return, the SKILL text alone never says "3.5 may repeat."

**Non-overlap.** A2-4 is a SKILL↔ENGINE mismatch (engine's `needsHuman` is single-valued via `.find`, while SKILL says "item(s)") — a *data-shape* contradiction, not the *control-flow* loop ambiguity. A5 E4 only notes escalation is *uncovered by evals*. Neither says the 3.5→4 path is an undocumented loop. Not in the 5 evolution.md findings. **Honest hedge:** an experienced reader will *infer* the loop (re-dispatch → notification → re-check `needsHuman`), so this is an under-specification footgun rather than a flat contradiction; a literalist who reads 3.5 as one-shot and then jumps to Phase 4 would, however, present an unverified escalation result, which the SKILL's own L61 invariant ("No unverified output reaches the user, ever") forbids.

## S3 — Phase 3 silently spans TWO turn boundaries (cost-gate turn-end + launch turn-end); the protocol never states that a single phase is multi-turn. **footgun**

Phase 3 is written as a 3-step linear list under one heading (SKILL:34–44). Two of those steps each end the turn, by the SKILL's own semantics:
- Step 1, the cost-gate (SKILL:35): "`AskUserQuestion` to confirm." AskUserQuestion blocks for the user's answer — the SKILL itself treats this family of calls as a "halt" (L19 "halt and `AskUserQuestion`"; L76 "halt"). Turn ends here, awaiting confirmation.
- Step 2, the launch (SKILL:36): "**Launch** (engine route; runs in the background, returns a task id, **your turn ends**)." Turn ends again.

So a single numbered phase ("3 — EXECUTE") contains **two** turn-ends with a user round-trip between them: the orchestrator stops after step 1, is re-invoked when the user confirms, *then* performs step 2 and stops again. Nowhere does the SKILL flag that Phase 3 is a multi-turn phase; the 1-2-3 numbering reads as a single contiguous sequence. A reader who expects steps 1→2→3 to execute in one turn is wrong about both boundaries.

**Why intra-SKILL / explicit non-overlap with A5 §4.** A5 §4 used the *first* turn-end (cost-gate) for a different purpose: to argue the eval2/eval3 expectations ("launches the workflow") are *uncheckable* in an autonomous single-turn harness. That is an *eval-checkability* consequence. My finding is the *protocol-statement* defect: that **two** turn boundaries live inside one phase (A5 names only the one cost-gate turn-end, and only to score evals), and that the SKILL never states Phase 3 is multi-turn. The novel element over A5 is the second turn-end (step 2's "your turn ends") compounding the first, turning Phase 3 into a two-stop phase — a sequencing fact about the protocol, independent of any eval. **Honest hedge:** the turn-ending nature of each step is individually stated (L35 implies it, L36 states it); the gap is purely that they are *bundled under one phase heading with no note that the phase spans turns*. Low harm to a careful reader, real trip-hazard to a literal one.

## N1 — The "read-only front-end / never mutates files / no mutating command" invariants are contradicted by Phase 2.5 instructing the orchestrator to run training/build/data-conversion jobs itself. **contradiction**

Three places assert the orchestrator never mutates:
- SKILL:3 (description): "**Read-only front-end; never mutates files.**"
- SKILL:7: "you **never** mutate files."
- SKILL:12 (Tool policy, Prohibited): "Edit/Write and **any mutating command** — those belong to sub-agents."

Phase 2.5 then directs the orchestrator to *itself* run (SKILL:28): "Pull any **training / build / data-conversion** / long-running items OUT of the work-list and **run them yourself via `Bash run_in_background: true`**". Training writes checkpoints/logs; builds write artifacts; data-conversion writes converted files — these are file-mutating side effects by definition, issued by a *mutating command* the orchestrator runs. SKILL:12 even **permits** that exact command in the same breath it prohibits mutation: "**Permitted:** … Bash (carve-out `run_in_background` …)" sits beside "**Prohibited:** … any mutating command." A training/build/convert job is precisely an "any mutating command," so the Permitted and Prohibited clauses of the *same line* collide, and both collide with the "never mutates files / read-only" absolutes at L3/L7.

**Why intra-SKILL.** Entirely within the SKILL: an Invariant/identity claim (L3, L7, L12-Prohibited) versus a Phase instruction and a Tool-policy permission (L28, L12-Permitted). No engine behavior is referenced — the carve-out runs "never inside a workflow" (L28).

**Non-overlap.** None of A1–A6 examine the read-only/no-mutation self-contradiction; A1/A2/A4/A6 are engine- or schema-facing, A3 is path portability, A5 is eval coverage. Not in the 5 evolution.md findings. **Honest hedge:** a literalist defense exists — "the orchestrator process doesn't directly `Edit`/`Write`; the spawned subprocess mutates the disk, so the orchestrator stays 'read-only.'" But L12 prohibits "any mutating **command**," and launching a build/train job *is* issuing a mutating command; and "never mutates files" describes the *effect*, which the carve-out plainly produces. The tension is genuine; whether you call it a contradiction or an unstated carve-out-shaped exception to the read-only rule, the SKILL never names the exception.

## N2 — Two unreconciled work-list confirmations: Phase 2 "Confirm the list with the user" (L26) and the Phase-3 cost-gate "AskUserQuestion to confirm" (L35) both gate the same work-list, adding an undocumented third turn boundary on the decompose→launch path. **gap / footgun**

Phase 2 (SKILL:26): "**Confirm the list with the user.** Pick a short `sessionId` …" — a user confirmation of the decomposed work-list.
Phase 3 step 1 (SKILL:35): "present **the work-list scope (item count + one-liners)** … `AskUserQuestion` to confirm."

Both steps present the work-list and ask the user to confirm it. The SKILL never says whether these are (a) the *same* confirmation described twice (in which case the duplication is redundant and the reader doesn't know which phase actually owns it) or (b) *two distinct* gates (in which case the user is asked to bless the same list twice, and — because Phase 2's "Confirm the list" is itself an AskUserQuestion-class halt — the decompose→launch path now contains **three** turn boundaries: Phase 2 confirm, Phase 3 cost-gate confirm, Phase 3 launch). Either way the protocol is under-specified: the relationship between the Phase-2 list-confirmation and the Phase-3 cost-gate is left undefined.

**Why intra-SKILL.** Two SKILL confirmation instructions (L26, L35) with no stated relationship; nothing engine-side.

**Non-overlap.** A5 §4 mentions Phase-2 "Confirm the list with the user" only to argue WorkItem *fields* may not be observable in conversation — it never flags the L26/L35 *duplicate-confirmation* relationship or the extra turn boundary it adds. No other deliverable touches it; not in the 5 evolution.md findings. **Honest hedge:** the most natural reading is that L26 is an informal in-conversation "does this list look right?" and L35 is the formal cost-gate — but the SKILL states neither that interpretation nor that L26 may be folded into L35, so a literal reader runs two gates.

## N3 — "Mandatory `/reflect`" (L9, L58) is contradicted by the change-of-mind exits (L76–77) that re-enter UNDERSTAND without reflecting, and Phase 5's "do not act until the user approves" presupposes a corrective action the read-only protocol never defines; Phase-5 timing relative to the 3.5 loop is also unspecified. **contradiction + gap**

The mandate is stated absolutely twice:
- SKILL:9: "every task that does invoke it gets the full cost-gate + **mandatory `/reflect`**."
- SKILL:58: "**5 — REFLECT.** Invoke `/reflect` via the Skill tool. **Mandatory.**"

But two reachable Edge-case paths exit the protocol *before* Phase 5, with no reflect:
- SKILL:76: "**User changes mind before launch:** halt, re-enter UNDERSTAND."
- SKILL:77: "**User changes mind after launch:** the background workflow completes; inform the user, then discard its result or stop it via `/workflows`; **re-enter UNDERSTAND.**"

In the L77 path a task was invoked, decomposed, cost-gated, and launched — i.e. it is squarely "a task that does invoke it" (L9) — yet it terminates at "re-enter UNDERSTAND" and never reaches the "mandatory" Phase-5 reflect on that abandoned orchestration. So the universal "every task … mandatory `/reflect`" (L9) is, read literally, violated by the change-of-mind exits.

Two further intra-SKILL wrinkles in Phase 5:
1. **"do not act until the user approves" (L58) presupposes an action the protocol forbids/omits.** The orchestrator is "read-only … never mutates files" (L3/L7) and /reflect "audits the *orchestration* (scope drift, dropped items, bad decomposition, a wrong CARVE-OUT or GATE call)" (L58). The corrective "act" implied by "do not act until the user approves" — re-decomposing, re-dispatching dropped items — is never defined as a phase (there is no Phase 6, and Phase 3.5 is scoped to engine-reported `needsHuman`, not reflect-found defects). So the clause guards against an action the SKILL neither lists nor routes.
2. **Phase-5 timing vs the S2 loop is unstated.** If Phase 3.5 re-dispatches one or more times (S2), the SKILL never says whether /reflect fires once after the *final* synthesize or after each loop iteration. Given L58 is "Mandatory" and Phase 4/5 are written linearly after 3.5, a reader cannot tell.

**Why intra-SKILL.** All citations are SKILL prose contradicting other SKILL prose (L9/L58 vs L76–77; L58 vs L3/L7); no engine behavior involved.

**Non-overlap.** The 5 evolution.md findings record the *design decision* that /reflect is mandatory with no proportional scaling (known finding #3) — they do **not** observe that the change-of-mind exits contradict the mandate, nor the "do not act" under-specification, nor the loop-timing gap. No A1–A6 deliverable addresses Phase 5 coherence. **Honest hedge:** "re-enter UNDERSTAND" could be read as "start a fresh orchestration whose eventual completion will reflect," making the abandoned attempt's missing reflect intentional; but L9's "every task that does invoke it" is unqualified, so the literal contradiction stands. The "do not act" clause may simply be boilerplate caution; I flag it as under-specified rather than a hard contradiction.

## N4 — Phase 2.5 can empty the work-list, but the GATE (L30–32) offers only "engine" or "clarify" and Phase 3 would launch an empty list — no "nothing left after carve-out" branch. **gap (minor)**

Phase 2.5 (SKILL:28) removes "training / build / data-conversion / long-running items" from the work-list. If the request consists *entirely* of such items (e.g. "retrain the baseline and rebuild the dataset"), the post-carve-out work-list is empty. The GATE (SKILL:30–32) then has only two routes — "**actionable & scoped → deterministic engine**" (L31) or "**still ambiguous → clarify**" (L32) — neither of which is "the work-list is now empty; there is nothing to launch." Following the prose, an empty-but-unambiguous list routes to "engine" and Phase 3 launches a zero-item workflow. The SKILL provides no guard for the carve-out-empties-the-list state.

**Why intra-SKILL.** It is a missing branch in the SKILL's own GATE/Phase-3 logic, derivable from Phase 2.5's removal step alone.

**Non-overlap.** A1-B9 / A2 (early-exit) discuss the *engine's* empty-`items` return — a different artifact. My point is the *SKILL prose* never anticipates the empty list that its own Phase 2.5 can produce. **Honest hedge:** low harm — the engine handles an empty list gracefully (per A1/A2), so the practical outcome is a no-op workflow and an empty Phase-4 report rather than a crash. This is a prose-completeness gap, not a failure; included for completeness, flagged minor.

## N5 — The change-of-mind Edge cases (L76–77) implicitly assume a single Phase-3 launch and do not cover a change of mind during the Phase-3.5 re-launch loop. **gap**

The Edge-case section enumerates exactly two change-of-mind states (SKILL:76–77): "before launch" and "after launch." Both are written against the *Phase-3* launch. But Phase 3.5 (SKILL:46) performs *another* background launch ("re-dispatch … as a fresh scoped `Workflow`"), so "the user changes mind after launch" can recur during the escalation loop. For that recurrence, L77's prescription — "discard its result or stop it via `/workflows`; **re-enter UNDERSTAND**" — is a poor fit: the *main* run already completed and produced partial results the user may want to keep, so wholesale "re-enter UNDERSTAND" (discarding everything) is heavier than the situation warrants. The Edge-case coverage simply doesn't contemplate the 3.5 re-launch as a distinct "launch" that change-of-mind could interrupt.

**Why intra-SKILL.** The Edge-case section (L76–77) under-covers a state the SKILL's own Phase 3.5 (L46) creates; no engine behavior involved.

**Non-overlap.** This is the edge-case facet the objective flagged; it is distinct from S2 (S2 = the 3.5→4 *control-flow loop* ambiguity; N5 = the *Edge-case section's* failure to cover change-of-mind *within* that loop). No A1–A6 deliverable or evolution.md finding addresses it. **Honest hedge:** one could argue L77 is meant to generalize to "any launch," but it literally says "the background workflow completes … re-enter UNDERSTAND," which presumes a single terminal run, not a mid-escalation partial state.

## Bottom line

Read as a standalone control-flow spec, `SKILL.md` has three confirmed seed defects (S1 carve-out-before-confirm, S2 undescribed 3.5→4 loop, S3 two turn-ends inside Phase 3) plus five additional intra-SKILL issues: a flat read-only/no-mutation contradiction with the Phase-2.5 carve-out (N1), a duplicated/under-specified work-list confirmation (N2), a "mandatory /reflect" that the change-of-mind exits silently skip together with an undefined "do not act" corrective and unstated Phase-5/loop timing (N3), an unhandled empty-after-carve-out list (N4, minor), and an Edge-case section that never contemplates change-of-mind during the 3.5 re-launch (N5). The strongest are N1 (a literal self-contradiction) and S1/S2 (sequencing footguns that can start expensive work before confirmation and leave a multi-turn loop undefined). Where a finding rests on one reading, it is flagged as such above.
