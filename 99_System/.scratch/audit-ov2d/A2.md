## FINDING A2-1 — The cost-gate's "+ critic" term badly under-counts; the impl/verify term is actually accurate

**SKILL L35** (Phase 3, cost-gate):
> "present the work-list scope ... and a rough agent estimate (≈ items × 2, × up to maxRounds on contested items, **+ critic + finalizer**)."

What the engine actually spends on the critic phase:

**ENG L18:** `const CRITIC_ROUNDS = 2` — the critic is a *loop*, not a single agent.
**ENG L295:** `for (let critRound = 1; critRound <= CRITIC_ROUNDS; critRound++) {` — up to 2 critic spawns.
**ENG L296-309:** each round spawns one critic agent.
**ENG L315-324:** every gap the critic returns is turned into a fresh work-item and dispatched through the *full* implement→verify loop:
> `const gapResults = await Promise.all(gapItems.map((g) => implementAndVerify(g)))`

`implementAndVerify` (ENG L212-252) runs up to `MAX_ROUNDS` rounds, and **each round spawns BOTH an implementer and a verifier** (ENG L216 + L221). So a single contested gap-item costs up to `MAX_ROUNDS × 2 = 8` agents — and the critic can emit *several* gaps per round, across 2 rounds.

**Conclusion:** "+ critic" presents the critic as a fixed single agent. The real critic-phase cost is up to `CRITIC_ROUNDS` critic agents **plus an unbounded fan-out of gap-items each costing up to 8 agents** (bounded only by `MAX_AGENTS`). The estimate has **no term at all** for critic-generated gap work. This is a genuine, material under-count.

**Precision note (so the reviewer can trust the rest):** the *impl/verify* portion of the same formula is NOT a mismatch. Read multiplicatively, "items × 2, × up to maxRounds on contested items" yields, for one fully-contested item, `2 × MAX_ROUNDS = 2 × 4 = 8` — which exactly matches the engine's worst case of `MAX_ROUNDS` implementers + `MAX_ROUNDS` verifiers (ENG L215-225, MAX_ROUNDS=4 at ENG L17). A mixed example confirms the product reading: 5 items, 2 contested → formula `3×2 + 2×8 = 22`; engine `3×2 + 2×8 = 22`. So the "= 8 agents, not 2" worry only holds if a reader collapses the formula to a flat `items × 2`; the written formula's "× up to maxRounds on contested items" clause does cover it. The defensible, indisputable under-count is the **critic/gap term**, not the impl/verify term. The "+ finalizer" term is also accurate — exactly one finalizer is spawned (ENG L367).

Severity: medium. A run that confirms a small estimate at the gate can balloon through critic gap-items.

## FINDING A2-2 — Documented return shape is wrong: SKILL says "returns only {4 fields}", engine returns 6 keys and richer items

**SKILL L43:**
> "the workflow ... returns **only** `{ finalReportPath, shortSummary, items:[{id,status}], needsHuman }`. Do not re-implement any of it."

**ENG L400-407** (the real return):
```
return {
  sessionId,                                                       // L401  — UNDOCUMENTED
  finalReportPath,                                                 // L402
  shortSummary: shortSummary || `${approvedCount}/...`,            // L403
  items: cleanResults.map((r) => ({ id: r.id, status: r.status, outputPath: r.outputPath })), // L404
  needsHuman,                                                      // L405
  agentsSpawned: agentCount,                                       // L406  — UNDOCUMENTED
}
```

Three concrete divergences, all quotable:

1. **`sessionId`** is returned (ENG L401) but absent from the SKILL's "only {...}" list (SKILL L43).
2. **`agentsSpawned`** is returned (ENG L406) but absent from the SKILL list (SKILL L43). (Ironically this is the one field that would let the orchestrator surface the realized agent count vs the gate estimate from A2-1 — yet the SKILL doesn't acknowledge it exists.)
3. **Items carry `outputPath`** — ENG L404 maps each item to `{ id, status, outputPath }`, but SKILL L43 documents `items:[{id,status}]` (two fields only). Phase-4 synthesis (SKILL L48-56) never references the per-item `outputPath`, so the field the engine surfaces is undocumented and unused by the protocol.

The word **"only"** in SKILL L43 makes this a true contradiction rather than a harmless omission: the engine returns a strict superset of what is documented.

Supporting: the **early-exit return is itself inconsistent** with the main return. ENG L45 (empty work-list) returns `{ sessionId, finalReportPath: null, shortSummary, items: [], needsHuman: null }` — note it includes `sessionId` but **omits `agentsSpawned`**, so the engine's own two return sites don't agree on the shape either.

Severity: low-medium. Won't crash (the front-end reads named fields), but the SKILL's contract is inaccurate and could mislead a maintainer who codes against the documented "only {...}".

## FINDING A2-3 — MAX_AGENTS=60 is never surfaced to the user, despite the transparency invariant; the cap fires silently and re-routes to a confusing escalation

**SKILL L67** (Cost control) names the cap but gives **no value**:
> "Inside the engine: `MAX_ROUNDS` on every verify loop, the engine concurrency cap, and a fixed **`MAX_AGENTS`** backstop."

**SKILL L64** (Invariants) promises full cost transparency:
> "**Transparency:** the GATE decision, carve-outs, and **cost estimate** are always surfaced to the user."

**SKILL L35** (the only user-facing cost surface) presents the agent *estimate* but contains **no mention of any ceiling**.

The engine, by contrast:

**ENG L16:** `const MAX_AGENTS = 60      // runaway-loop backstop across the whole run`
**ENG L147-151:** once `agentCount >= MAX_AGENTS`, `spawn` returns `null` *silently* (it logs once, but the front-end's turn already ended):
```
if (agentCount >= MAX_AGENTS) { ... hitCap = true; return null }
```
**ENG L226 / L237:** a null impl/verdict is treated as "not approved", so capped items fall through to `needs-human`.
**ENG L345-346:** the run then returns
> `needsHuman = { item: null, reason: \`MAX_AGENTS (${MAX_AGENTS}) reached before all work completed\`, context: null }`

**Mismatch:** the user is asked to confirm a launch at the gate (SKILL L35) with an estimate but is **never told the hard ceiling is 60**. A confirmed work-list whose true cost (see A2-1's critic/gap fan-out) exceeds 60 will silently cap mid-run and surface a `needsHuman` whose `item` is `null` and whose reason cites a number ("MAX_AGENTS (60)") the user never saw at the gate. SKILL L64 claims cost is "always surfaced"; the binding cap is not. This is a documentation/behavior consistency gap with a concrete confusing failure mode.

Severity: medium.

## FINDING A2-4 — Phase-3.5 escalation assumes a multi-item channel and an `objective` field; `needsHuman` is single-valued and carries only an item *id*

**SKILL L46** (Phase 3.5):
> "if `needsHuman` is non-null: surface it via `AskUserQuestion` (**objective**, why it stalled, last blockers), then re-dispatch ONLY the escalated **item(s)** ... (one or few items ...)."

The engine's `needsHuman` is a **single object selected by `.find()` (first match only)**, and its shape is `{ item, reason, context }` — no `objective`:

**ENG L334:** `const escalated = results.find((r) => r._escalate)` — `Array.find` returns the **first** escalated item; any other items that also exhausted their verify rounds are dropped from this channel.
**ENG L336-347:** `needsHuman` is then exactly one of:
- `escalated._escalate` = `{ item: <id>, reason, context: feedback }` (built at ENG L246-250),
- blocked → `{ item: <id>, reason, context: _blockedBy }` (ENG L340-343),
- hitCap → `{ item: null, reason, context: null }` (ENG L346).

Two concrete divergences:

1. **"item(s)" (plural) vs a single-valued channel.** SKILL L46 says re-dispatch "the escalated item(s)" and "one or few items", implying `needsHuman` can convey multiple escalations. It cannot — ENG L334's `.find()` yields one. If three items each blow through `MAX_ROUNDS`, only the first appears in `needsHuman`; the other two are present only as `status:'needs-human'` rows inside the returned `items[]` array (ENG L404, via L239-251). SKILL L46 keys the entire escalation step off `needsHuman` and never instructs the orchestrator to scan `items[]` for additional `needs-human` rows — so the surplus escalations are silently left unverified, in tension with the SKILL L61 invariant "No unverified output reaches the user, ever."

2. **"objective" is not in the payload.** SKILL L46 tells the orchestrator to surface the `objective`, but `needsHuman` carries `item` = the *id string* (ENG L246: `item: item.id`), not the objective text. The orchestrator must re-derive the objective from its in-conversation work-list; the engine does not hand it over. Likewise "last blockers" only exists for the escalated branch (`context: feedback`); the blocked branch puts dependency ids in `context` (ENG L342) and the hitCap branch sets `context: null` (ENG L346), so "last blockers" is not reliably present.

Severity: medium (point 1 — silent loss of surplus escalations) / low (point 2 — field-name slippage).

## FINDING A2-5 — SKILL guarantees a durable `_REPORT.md` to read in Phase 4, but the engine can return a non-null `finalReportPath` to a file that was never written

**SKILL L43:** "it **writes one durable `_REPORT.md`**".
**SKILL L48** (Phase 4): "Present from the workflow's pointer return — **read `finalReportPath`**, do not reconstruct a blob from raw outputs".

The report is written by a *spawned finalizer agent*, which is itself subject to the agent cap:

**ENG L367-389:** `const finalizer = await spawn([ ... ], { label: 'finalize:report', ... })` — the finalizer is the agent that writes `finalReportPath` (ENG L381).
**ENG L147-151:** if `agentCount >= MAX_AGENTS` already, `spawn` returns `null` → `finalizer` is `null` → **no file is written**.
**ENG L390:** `if (finalizer && finalizer.shortSummary) shortSummary = ...` — null finalizer is tolerated; the run continues.
**ENG L402:** the return nonetheless hands back `finalReportPath` (a non-null path string computed at ENG L41), and **ENG L403** falls back to a synthesized `shortSummary`.

**Mismatch:** when the cap is hit before Finalize (precisely the A2-3 scenario), the engine returns a populated `finalReportPath` even though the finalizer never ran and the `_REPORT.md` does not exist on disk. An orchestrator faithfully following Phase 4 (SKILL L48, "read `finalReportPath`") would attempt to read a missing file. The SKILL's "writes one durable `_REPORT.md`" (L43) is therefore not an invariant the engine actually upholds under the cap.

Severity: low-medium (only triggers on the MAX_AGENTS path, but that path is exactly where the user most needs the report).
