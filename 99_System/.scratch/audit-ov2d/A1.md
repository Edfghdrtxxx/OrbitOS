# A1 — Engine correctness/logic bugs: `orchestrate-inline.workflow.js`

Audit target: `D:/Something/research/MATE-Automation-V4/.agents/skills/orchestrate-v2-D-workflow/workflows/orchestrate-inline.workflow.js` (408 lines).
SKILL context: `…/orchestrate-v2-D-workflow/SKILL.md`.
Method: every claim below is quoted against the actual lines; two of the JS-semantics claims (B1 cycle crash, B1 backstop-induced cycle) were additionally reproduced with `node`. None of these duplicate the 5 already-known findings or the recorded `/reflect` outcomes.

Severity legend: **blocker** = corrupts output / crashes the run / returns a lie; **sharp-edge** = wrong under plausible inputs, silent; **nit** = cosmetic / inconsistency.

## B1 — Dependency cycle is NOT detected: it hard-crashes the whole run with a stack overflow (no deadlock, no escalation). **blocker**

Scheduler, lines 259-280:
```js
const promises = new Map()
function run(item) {
  if (promises.has(item.id)) return promises.get(item.id)          // 261
  const p = (async () => {
    const deps = item.dependsOn.map((d) => byId.get(d)).filter(Boolean)
    const depResults = await Promise.all(deps.map(run))            // 264  <-- first await
    ...
  })()
  promises.set(item.id, p)                                          // 278  <-- memo set AFTER
  return p
}
```
The memoization guard at line 261 is defeated for cycles because `promises.set(item.id, p)` (line 278) runs only *after* the IIFE expression on line 262 has been constructed — but calling `(async () => {…})()` executes the body **synchronously up to the operand of the first `await`**, and that operand is `Promise.all(deps.map(run))` (line 264). Evaluating `deps.map(run)` synchronously re-enters `run` for each dependency *before* line 278 ever executes. For a cycle A→B→A, `run(A)` calls `run(B)` calls `run(A)`, and on that re-entry `promises.has('A')` is still `false`. Result: unbounded synchronous mutual recursion → `RangeError: Maximum call stack size exceeded`, thrown out of `await Promise.all(items.map(run))` at line 284, aborting the entire workflow with no `needsHuman`, no report, no escalation.

Verified by reproduction (the exact pattern from 259-280): a two-item A↔B cycle throws `RangeError: Maximum call stack size exceeded`. So the objective's question ("detect or DEADLOCK?") resolves to **neither** — it crashes. (A self-dependency `dependsOn:['A']` is the degenerate single-item trigger and crashes identically.)

This is reachable from a plausible front-end mistake *amplified by the engine's own same-file backstop*, not just hand-malformed input. Reproduced: given `A{dependsOn:['B'], outputPath:'P'}` listed first and `B{dependsOn:[], outputPath:'P'}`, the backstop loop (lines 54-60) appends `A` to `B.dependsOn` (because they share `outputPath` `P`), producing `A.dependsOn=['B']`, `B.dependsOn=['A']` — a cycle the engine itself manufactured. So a front-end that (a) says "A depends on B", (b) lists A before B, and (c) gives both the same `outputPath` gets a silent backstop-built cycle → crash.

Fix sketch: before scheduling, run a topological/cycle check over `items`+`dependsOn` (or maintain a `visiting` set inside `run` and return a `status:'blocked'` cycle result instead of recursing); at minimum set the memo to an in-flight placeholder *before* awaiting deps so a re-entry is caught.

## B2 — When `MAX_AGENTS` is hit, the FINALIZE report is never written, yet the run returns `finalReportPath` as if it exists. **blocker**

`spawn` returns `null` (does not throw) once capped, lines 146-154:
```js
if (agentCount >= MAX_AGENTS) { … return null }
```
The FINALIZE writer is itself a `spawn` (line 367) and is the agent that actually *writes the report file* (its prompt, lines 380-381, instructs it to "Write a consolidated Markdown report to `${finalReportPath}`"). On a capped run `finalizer` is `null`, so line 390 (`if (finalizer && finalizer.shortSummary)`) is skipped and **no file is written**. But the return still hands back `finalReportPath` unconditionally (line 402):
```js
return { sessionId, finalReportPath, shortSummary: … , items, needsHuman, agentsSpawned }
```
`finalReportPath` is a path to a file that does not exist on disk. SKILL Phase 4 then instructs the orchestrator to `read finalReportPath` ("read `finalReportPath`, do not reconstruct a blob") — that read fails. The entire point of FINALIZE (a single durable deliverable) is silently void exactly on the large runs (the 60-agent class) that motivated it. `needsHuman` is set for `hitCap` (line 346) only if no escalation/blocked precedes it (see B3), so the missing-report condition is not even reliably signalled.

Fix sketch: after the finalize spawn, if `finalizer` is null (or the file is absent), set `finalReportPath = null` in the return and fold a "report not generated (cap reached)" note into `shortSummary`/`needsHuman`.

## B3 — `results.find(...)` surfaces only the FIRST stall; additional escalations and all-but-first blocked items are silently dropped from `needsHuman`. **sharp-edge**

Lines 334-347:
```js
const escalated = results.find((r) => r._escalate)       // 334
const blocked   = results.find((r) => r.status === 'blocked')  // 335
…
if (escalated)      needsHuman = escalated._escalate
else if (blocked)   needsHuman = { item: blocked.id, … }
else if (hitCap)    needsHuman = { item: null, … }
```
`.find` returns one element. If three items each exhaust their verify loops (each carries `_escalate` from line 246), only the first becomes `needsHuman`; the other two stalls exist only as `status:'needs-human'` rows inside `items[]`. SKILL Phase 3.5 tells the orchestrator to "surface `needsHuman`… re-dispatch ONLY the escalated item(s)" — `needsHuman.item` is a single id, so the other stalled items are never re-dispatched unless the orchestrator independently scans `items[]` (which the SKILL never instructs). Same for multiple `blocked` items. The `escalated`-before-`blocked`-before-`hitCap` precedence also means a cap-induced stall (B8) or a blocked item is masked whenever any one escalation exists.

Fix sketch: build `needsHuman` as an array (`results.filter(r => r._escalate || r.status==='blocked')`) and have the SKILL re-dispatch all of them, or at least include a `stalls:[…]` count alongside the single primary.

## B4 — Completeness-critic gap items bypass dependency + same-file serialization and default `mutatesFiles:false`, mis-framing mutating gaps as content-producers. **sharp-edge**

Gap construction + dispatch, lines 315-324:
```js
const gapItems = critic.gaps.map((g) => ({
  …
  mutatesFiles: g.mutatesFiles === true,   // 321  default false
  dependsOn: [],                            // 322  always empty
}))
const gapResults = await Promise.all(gapItems.map((g) => implementAndVerify(g)))  // 324
```
Three concrete defects, all confirmed:
1. **No serialization.** Gap items are run via `implementAndVerify` directly (line 324), **not** via `run`, so they never pass through the `lastWriterOfPath` backstop (lines 53-60) and never get dependency scheduling. Two gaps in the same critic round that share an `outputPath`, or that mutate the same file, run concurrently with no worktree (the file's own comment, lines 24-28, says same-file writes "MUST be serialized") → lost writes / race.
2. **`dependsOn:[]` is hard-wired** (line 322), so even if the critic identifies a gap that logically depends on another gap, ordering is impossible.
3. **`mutatesFiles` defaults to false.** `CRITIC_SCHEMA` makes `mutatesFiles` optional (only `id`, `objective`, `outputPath` are required — lines 113), so it is usually absent → `g.mutatesFiles === true` is false. A gap that is actually a mutation (e.g. "fix the off-by-one in `foo.js`") is then handed the **content-producer** prompt branch (line 180: "This item is a content producer. Write the deliverable to `outputPath`"), telling the implementer to author a new file instead of editing the existing one — wrong framing for a fix.

Fix sketch: route gap items through `run` (after re-running the same-file backstop over `items.concat(gapItems)`), and either require `mutatesFiles` in `CRITIC_SCHEMA` or infer it (default true for gaps whose `objective` implies an edit).

## B5 — The same-file backstop keys on `outputPath`, which for mutators is the REPORT path, not the file being mutated — so two mutators editing the same source slip through. **sharp-edge**

Backstop, lines 53-60, keys `lastWriterOfPath` on `it.outputPath`. But the implementer prompt for `mutatesFiles:true` (lines 178-179) says: "Write your changes DIRECTLY to the real working tree … Then write a short report to `${item.outputPath}`." For a mutator, `outputPath` is the **report location**, *not* the source file being edited. Two mutating items that both edit `src/foo.js` but write their reports to `…/A-report.md` and `…/B-report.md` have *distinct* `outputPath`s, so the backstop never serializes them — they run concurrently against the same source file with no worktree isolation. The "additional backstop" advertised in lines 26-28 gives false confidence: it can only see report paths, never the actual mutated files, so for the exact case it is meant to protect (concurrent same-source edits) it is blind. The front-end-set `dependsOn` is the *only* real protection, despite the code presenting itself as a safety net.

Fix sketch: give `WorkItem` an explicit `mutatesPaths:[…]` (the real files touched) and key the backstop on those for mutators, falling back to `outputPath` only for content-producers.

## B6 — A dangling / mistyped `dependsOn` id is silently dropped, losing the intended serialization (same-file race). **sharp-edge**

Line 263:
```js
const deps = item.dependsOn.map((d) => byId.get(d)).filter(Boolean)
```
`byId.get(d)` returns `undefined` for any id not present in `items`; `.filter(Boolean)` removes it with no warning. A front-end typo in a dependency id (`'item-3'` vs `'item3'`) therefore makes the item run as if it had **no** such dependency — it parallelizes when it should have waited. For a same-file pair whose ordering relied on that (now-dropped) dep, this is a silent concurrent-write data race, the precise failure the whole serialization design exists to prevent. No log, no `needsHuman`.

Fix sketch: validate every `dependsOn` id against `byId` up front; on a dangling reference, `log` a warning and mark the item `blocked` (or fail fast) rather than silently dropping the edge.

## B7 — Same-file detection is exact-string `outputPath` equality, defeated by path-normalization variants. **nit** (sharp-edge on Windows)

The backstop (line 55, `lastWriterOfPath.has(it.outputPath)`) and the final return both compare `outputPath` by exact string. `foo/bar.md`, `./foo/bar.md`, `foo\bar.md` (Windows), and absolute-vs-relative spellings of the same file are treated as distinct keys → not serialized → concurrent writes. Given the repo is on Windows (mixed `/` and `\` are common), this is more than cosmetic.

Fix sketch: normalize (`path.resolve` / `path.normalize`, case-fold on Windows) before using `outputPath` as the serialization key.

## B8 — Cap-induced stalls are mislabeled "verify loop exhausted 4 rounds", and the accurate `MAX_AGENTS` message is shadowed. **nit**

When `spawn` returns `null` mid-item (cap reached), `implementAndVerify` still spins all `MAX_ROUNDS` rounds (both spawns return null instantly) and returns `needs-human` with `_escalate.reason = "verify loop exhausted ${MAX_ROUNDS} rounds without approval"` (line 248) — but the real cause is the cap, not four substantive failed reviews. Because `escalated` (line 334) is checked before `hitCap` (line 345 `else if`), the more accurate `MAX_AGENTS (60) reached before all work completed` message (line 346) is never surfaced. The escalation the human sees points at the wrong cause.

Fix sketch: in `spawn`/`implementAndVerify`, distinguish a null-from-cap return and set `_escalate.reason` to the cap; or check `hitCap` before `escalated` in the precedence chain.

## B9 — Return shape is inconsistent: the empty-items early return omits `agentsSpawned`, and `items[]` carries more than SKILL documents. **nit**

Normal return (lines 400-407) yields `{ sessionId, finalReportPath, shortSummary, items, needsHuman, agentsSpawned }`. The empty-work-list early return (line 45) yields `{ sessionId, finalReportPath: null, shortSummary, items: [], needsHuman: null }` — **no `agentsSpawned`**. A consumer reading `result.agentsSpawned` gets `undefined` on the empty path but a number on the normal path. Separately, SKILL line 43 documents the return `items` as `[{id,status}]`, while the engine returns `[{id,status,outputPath}]` (line 404) and adds undocumented top-level `sessionId`/`agentsSpawned` — harmless drift, but drift.

Fix sketch: include `agentsSpawned: 0` in the line-45 return and reconcile the SKILL's documented return shape with the engine's.

## B10 — The FINALIZE writer is unpaired (no skeptic) and its file write is never confirmed — the one user-facing deliverable is the only unverified output. **nit / sharp-edge**

SKILL invariant (line 61): "Every implementer is paired with a skeptic … No unverified output reaches the user, ever." Yet the FINALIZE agent (single `spawn`, line 367) writes the consolidated `_REPORT.md` — the artifact the user actually reads — with **no** verify pairing, and the engine never checks that `finalReportPath` was actually created (it trusts the agent and returns the path, lines 390/402). The completeness critic (line 296) is likewise unpaired, but it is itself a reviewer; the *report writer* is a producer whose output reaches the user unverified, contradicting the stated invariant.

Fix sketch: after the finalize spawn, stat `finalReportPath` and, if absent or empty, escalate; optionally add a lightweight skeptic pass on the consolidated report.
