# A5 — EVALS coverage & quality audit (orchestrate-v2-D-workflow)

Scope: `evals/evals.json` (3 evals) vs. what `SKILL.md` (front-end protocol) and
`workflows/orchestrate-inline.workflow.js` (engine) actually promise. Goal: prove the
3 evals cover only FRONT-END behavior, identify the engine + edge-case coverage gaps,
test whether each existing expectation is actually *checkable*, and propose missing
evals. No files were created or edited (this is a coverage assessment only).

## 1. What the 3 existing evals actually exercise (front-end only — verified)

`evals.json` is a pure **black-box prompt-eval** format: each entry is
`{prompt, expected_output, files, expectations[]}` (`evals.json:3-49`). All three set
`files: []` (`evals.json:8, 20, 35`) and the `evals/` folder contains *only* `evals.json`
— no fixtures, no runner. So there is no on-disk tree for an implementer to read or
mutate; the engine has nothing to operate on even in principle.

- **eval1** "Fix the analysis code" (`evals.json:4-15`): exercises **Phase 0 EVOLVE**
  (`SKILL.md:17`), **Phase 1 Zero-Assumptions clarify** (`SKILL.md:19`) and the
  read-only tool policy (`SKILL.md:11-12`). Its expectations are all *halt* assertions —
  AskUserQuestion, no decompose/launch, no Edit/Write (`evals.json:12-14`).
- **eval2** "Review all Python scripts … replace hardcoded paths … unused imports"
  (`evals.json:16-32`): exercises **Phase 1 restate** (`SKILL.md:19`), context-gathering
  via general-purpose sub-agents (`SKILL.md:19`), **Phase 2 DECOMPOSE / same-file
  dependsOn** (`SKILL.md:21-26`), **Phase 2.75 GATE announce** (`SKILL.md:30-32`), and
  the **Phase 3 cost-gate + launch** (`SKILL.md:34-44`).
- **eval3** "Audit the results in outputs/figures/… Spawn a sub-agent … read memory"
  (`evals.json:33-48`): same front-end spine plus read-only WorkItems
  (`mutatesFiles:false`) and `finalReportPath` placement beside the artifact
  (`SKILL.md:36`).

**Every one of these assertions targets behavior the orchestrator emits in-conversation
BEFORE it hands off.** The deepest thing any eval checks is "launches the
orchestrate-inline workflow via the Workflow tool" (`evals.json:29`) — i.e. the *act of
launching*, never anything the launched engine does. The engine returns asynchronously
via a `<task-notification>` (`SKILL.md:44`); nothing in `expected_output`/`expectations`
references that return (`finalReportPath`, `items[].status`, `needsHuman`,
`shortSummary`) or any post-completion Phase 3.5/Phase 4 behavior. **Confirmed: 0/3 reach
the engine; coverage of the engine is zero by construction, not by accident.**

## 2. Engine behavior with ZERO coverage (all in scope — the engine lives inside this skill)

The skill's own description promises "fan out implementers each paired with a skeptic via
a deterministic Workflow that finalizes into one durable report" (`SKILL.md:3`), so the
engine is squarely within the skill's promised surface. None of it is touched:

- **E1 — implement→verify loop-until-approved (MAX_ROUNDS=4).** `implementAndVerify`
  (`orchestrate-inline.workflow.js:212-252`), `MAX_ROUNDS` (`:17`). No eval forces a
  first-round-wrong deliverable, so the loop, the re-feedback prompt
  (`:159-188`, the `feedback` re-injection), and the approve gate
  (`:226-236`) are unverified.
- **E2 — same-file serialization backstop (engine-side).** The engine *auto-chains* items
  sharing an `outputPath` even if the caller forgot `dependsOn`
  (`:48-60`, `lastWriterOfPath`). eval2 only checks the **orchestrator** sets `dependsOn`
  (`evals.json:25`); nothing checks the engine's independent backstop. These are two
  different safety nets and only the front-end one is (weakly) covered.
- **E3 — dependency scheduler + blocked-item handling.** `run()` parallelizes independent
  items and marks an item `blocked` when a dependency did not pass
  (`:259-280`), feeding `needsHuman` (`:339-343`). Untouched.
- **E4 — escalation / needsHuman channel + Phase 3.5 re-dispatch.** The `_escalate`
  object on loop exhaustion (`:246-251`), its promotion to `needsHuman`
  (`:334-338`), and the SKILL-side response — surface via AskUserQuestion then re-dispatch
  ONLY the escalated item(s) as a fresh scoped Workflow so the skeptic pairing holds
  (`SKILL.md:46`) — are entirely uncovered.
- **E5 — completeness critic (loop-until-dry, CRITIC_ROUNDS=2).** Runs only when
  `allApproved && !hitCap` (`:293-328`), re-dispatches dropped sub-tasks as `gap-N` items.
  Untouched.
- **E6 — FINALIZE + pointer-only return.** The single durable `_REPORT.md`
  (`:365-390`) and the compact return shape `{finalReportPath, shortSummary,
  items, needsHuman}` (`:400-407`) — plus the SKILL Phase 4 rule "read `finalReportPath`,
  do not reconstruct a blob" (`SKILL.md:48`) — are unverified.
- **E7 — MAX_AGENTS runaway backstop.** `spawn` returns `null` past the cap and that
  degrades cleanly to `needsHuman` (`:144-154, 345-347`). Untouched.
- **E8 — schema-robustness / no-spill (the 2026-06-24 abort-class guard).** The
  summary-only `IMPL_SCHEMA`/`FINAL_SCHEMA` with `additionalProperties:true`
  (`:70-88, 130-138`) and the "short summary, no spill" prompt guards
  (`:185, 386`). Untouched.
- **E9 — empty work-list early return.** `items.length===0 → {finalReportPath:null,
  shortSummary:'empty work-list', needsHuman:null}` (`:43-46`). The single cheapest,
  fully-deterministic test, and it is uncovered.

## 3. Orchestrator EDGE cases with ZERO coverage

- **O1 — Phase 2.5 CARVE-OUT.** Training/build/data-conversion/long-running items must be
  pulled OUT of the work-list and run by the orchestrator itself via
  `Bash run_in_background: true`, sequentially — never inside the workflow
  (`SKILL.md:28`). No eval prompt contains such an item: eval2 (path-rewrite + unused
  imports) and eval3 (read-only audit) are all fully workflow-able. **Real gap on a
  load-bearing, footgun-prone branch** (zombie shells if mis-routed, per the lesson it
  encodes).
- **O2 — Trivial task → decline to /dispatch.** The skill's headline boundary is "NOT for
  trivial chores (use /dispatch)" (`SKILL.md:3, 9`) and the explicit edge case "Trivial
  task: decline into /dispatch or direct action" (`SKILL.md:75`). **No eval ever feeds a
  trivial one-liner whose correct answer is to refuse to orchestrate.** eval1 is
  *ambiguous→clarify* (a different branch), eval2/eval3 are genuinely big. This is the
  single most important untested promise in the skill — its over-trigger boundary.
- **O3 — No-argument.** "ask what to orchestrate" (`SKILL.md:74`). Uncovered (eval1 is
  ambiguous-with-content, not empty).
- **O4 — User changes mind before/after launch** (`SKILL.md:76-77`). Uncovered; hard to
  express in a single-turn prompt eval (see §5), so lower priority.
- **O5 — mirror-diff-before-sync** (`evolution.md:50`). Coverage is zero, **but this is a
  /reflect-derived *maintenance* constraint about syncing the two real skill copies
  (`.agents/` vs `.claude/`), not a user-prompt-triggerable orchestration path.** A
  prompt-eval cannot naturally exercise it, and the skill does not promise it as a runtime
  behavior. I therefore flag it as *correctly* out of eval scope rather than a defect to
  paper over with a synthetic eval — proposing one would test behavior the skill doesn't
  promise to a user.

## 4. Checkability of the EXISTING expectations (several are NOT actually checkable)

The harness is autonomous (no human answers AskUserQuestion; `evals.json` ships no
answer-injection mechanism). Under that reality:

- **eval1 — internally consistent and checkable.** All four expectations
  (`evals.json:11-14`) are satisfiable in one turn: read evolution.md, AskUserQuestion,
  and *absence* of decompose/launch/Edit/Write. The clarify-halt naturally ends the turn,
  and that is exactly what the eval wants. Good eval.

- **eval2 / eval3 contain a structural contradiction.** The cost-gate is a **mandatory
  AskUserQuestion that ends the turn** ("AskUserQuestion to confirm. The launch is never
  silent", `SKILL.md:35`) and **Launch happens only afterward** (`SKILL.md:36`,
  step 2 after step 1). So in a single autonomous run the orchestrator *correctly* stops
  at the cost-gate and **never reaches the launch**. That makes these expectations
  **uncheckable as written**:
  - eval2 "launches the orchestrate-inline workflow via the Workflow tool"
    (`evals.json:29`),
  - eval3 "cost-gates and launches … via the Workflow tool" + "sets `finalReportPath` so
    the consolidated report lands beside the audited artifact" (`evals.json:44-45`).
  `finalReportPath` is only emitted inside the Workflow `args` (`SKILL.md:36-42`), which
  is post-gate; the cost-gate announcement is only required to surface scope + carve-outs
  + agent estimate (`SKILL.md:35`), not `finalReportPath`. So a faithful agent scores a
  FALSE NEGATIVE on these lines. A judge that nonetheless "passes" them is rewarding an
  agent that launched *without* waiting for cost-gate confirmation — i.e. the eval as
  written can only pass by violating the skill.

- **Weakly checkable (verbalization-dependent).** "decomposes into a numbered WorkItem
  work-list (id, objective, outputPath, mutatesFiles, dependsOn)" and "sets dependsOn
  between same-file items" (`evals.json:24-25`), and eval3's `mutatesFiles:false`
  (`evals.json:42`). Phase 2 only requires a work-list "in conversation" then "Confirm
  the list with the user" (`SKILL.md:21-26`); it does **not** mandate that every internal
  field (outputPath/mutatesFiles/dependsOn) appear in the conversational draft. Those
  fields are guaranteed only in the Workflow `args`, which is post-gate and never reached.
  So these are checkable only if the agent happens to verbalize the full struct — not a
  hard observable.

- **Soft internal inconsistency in eval3.** `expected_output` says the orchestrator
  itself "reads relevant memory" and the expectation says "reads the corresponding
  memory" (`evals.json:36, 40-ish`), yet the tool policy/Phase-1 rule is "gather context
  by dispatching sub-agents, not by reading files yourself" (`SKILL.md:14, 19, 63`).
  Memory files are small index files (arguably allowed like evolution.md), but the eval
  bakes in a self-read that tensions with the no-self-deep-read invariant. At minimum it
  is ambiguous what a correct agent should do, which makes that line a coin-flip for the
  judge.

- **Cleanly checkable across all three:** "reads evolution.md as part of Phase 0"
  (observable Read of `evolution.md`) and "does NOT use Edit/Write or mutating Bash"
  (observable *absence* of mutating tool calls) — `evals.json:10, 14 / 21, 30 / 39, 46`.
  These are the most robust assertions in the file and should be retained verbatim.

## 5. Proposed missing evals (described in prose; no file written)

### 5a. New PROMPT-evals (same `evals.json` format; checkable by the existing harness because each correctly *halts* before launch)

- **PE-A · Trivial → decline (covers O2).** Prompt: a true one-liner, e.g. *"Rename the
  variable `tmp` to `buffer` in `utils.py`."* `expected_output`: orchestrator recognizes
  this is below the orchestration threshold and declines into `/dispatch` or direct
  action; it does NOT decompose, cost-gate, or launch. Key expectations: reads
  evolution.md; **no** work-list; **no** Workflow launch; explicit hand-off to `/dispatch`
  (per `SKILL.md:9, 75`); no Edit/Write. This guards the skill's own over-trigger
  boundary — currently untested.

- **PE-B · Carve-out (covers O1).** Prompt mixing a long-running training/build item with
  analysis, e.g. *"Retrain the ResNet baseline on the new split, then audit the resulting
  confusion matrices and write up which classes regressed."* `expected_output`:
  orchestrator pulls the *retrain* out as a Phase-2.5 carve-out, states it will run that
  itself via `Bash run_in_background` sequentially (NOT inside the workflow), and routes
  only the audit into the work-list. Key expectations (all observable pre-gate): announces
  the carve-out transparently (`SKILL.md:28, 64`); the training step is **not** an Agent
  dispatch and **not** a Workflow item; the audit items are decomposed normally; reaches
  (and stops at) the cost-gate. This tests the most footgun-prone branch (zombie shells).

- **PE-C · No-argument (covers O3).** Prompt: bare *"/orchestrate"* / *"orchestrate"* with
  no object. `expected_output`: AskUserQuestion asking what to orchestrate (`SKILL.md:74`);
  no decomposition; no mutation. Cheap, cleanly checkable.

- **PE-D (optional) · Over-broad/ambiguous-but-big** to disambiguate the eval1 *clarify*
  branch from the PE-A *decline* branch — ensures the judge distinguishes "too vague"
  from "too small."

### 5b. New ENGINE integration tests (different modality — direct `Workflow` invocation with fixtures; CANNOT live in the current prompt-eval `evals.json` and should be noted as such)

These exercise §2's E1–E9 by invoking the workflow directly with a synthetic
`{sessionId, objective, items, finalReportPath}` and asserting on the deterministic return
(`orchestrate-inline.workflow.js:400-407`) and `log`/`phase` trace. They need a fixture
tree + a runner the repo does not yet have, so they belong in a separate harness, not in
`evals.json` (flagging the modality mismatch is part of the finding).

- **ENG-1 · verify loop.** One item engineered so round 1 is wrong; assert `rounds>1` and
  eventual `status:'approved'`, or `status:'needs-human'` + `_escalate.reason` =
  "verify loop exhausted" after `MAX_ROUNDS` (`:215-251`). Asserts no unverified output
  passes.
- **ENG-2 · escalation/needsHuman.** A never-approvable item; assert top-level
  `needsHuman.reason` mentions the exhausted loop and that any sibling approved items stay
  `approved` (`:334-338, 349-356`).
- **ENG-3 · same-file backstop.** Two items sharing one `outputPath`, caller sets **no**
  `dependsOn`; assert the engine injected the chain so they serialize (`:48-60`) — they do
  not run concurrently.
- **ENG-4 · blocked dependency.** B `dependsOn` A; force A to fail; assert B
  `status:'blocked'`, `_blockedBy:[A]`, and `needsHuman` set from the blocked branch
  (`:259-280, 339-343`).
- **ENG-5 · completeness critic.** All items pass but the objective implies a dropped
  sub-task; assert the critic fires (only because `allApproved`), emits a `gap-N` item,
  re-dispatches it, and stops at `CRITIC_ROUNDS` (`:293-328`).
- **ENG-6 · FINALIZE/pointer.** Assert exactly one report at `finalReportPath`, that the
  return is pointer-only (no full blob in `shortSummary`), and `items[]` carries
  `{id,status,outputPath}` only (`:365-407`). Encodes the 22-agent-truncation lesson
  (`evolution.md:47`).
- **ENG-7 · MAX_AGENTS cap.** Drive spawns past `MAX_AGENTS`; assert `spawn` returns
  `null`, work degrades to `needsHuman` with reason mentioning `MAX_AGENTS`
  (`:144-154, 345-347`).
- **ENG-8 · no-spill schema.** Feed an implementer return that crams content into
  `summary`; assert the run still completes (lenient `additionalProperties:true`,
  required-`summary`-only) rather than aborting (`:70-88, 130-138`; `evolution.md:36-38`).
- **ENG-9 · empty work-list.** `items:[]` → `{finalReportPath:null,
  shortSummary:'empty work-list', needsHuman:null}` (`:43-46`). Cheapest deterministic
  unit test; should exist.

### 5c. Fixes to the EXISTING evals (checkability, not new coverage)

- **Resolve the eval2/eval3 cost-gate-vs-launch contradiction (§4).** Either (a) split the
  launch expectation into two phases and have the harness inject a "confirm" answer to the
  cost-gate AskUserQuestion, then assert the post-confirm Workflow `args` (including
  `finalReportPath`); or (b) reword to terminal-state-honest expectations: *"presents a
  cost-gate via AskUserQuestion and **halts** awaiting confirmation; the announced plan
  names the orchestrate-inline workflow as the route and (eval3) names a `finalReportPath`
  beside the audited artifact."* Without one of these, a faithful agent fails the line and
  a passing agent is one that launched without confirmation.
- **Make the WorkItem-field expectations observable** by either requiring the confirmed
  work-list to surface `outputPath`/`mutatesFiles`/`dependsOn` in conversation (a small
  SKILL Phase-2 tweak point), or downgrading those expectations to what is actually
  visible pre-gate.
- **Disambiguate eval3's "reads memory"** against the no-self-deep-read invariant — either
  scope it explicitly as an allowed small-index read, or route it through the
  context-gathering sub-agent the same prompt already requests.

## 6. Bottom line

- **Verified:** all 3 evals test only front-end orchestration and stop at/just before the
  Phase-3 hand-off; **none** reach the engine (E1–E9) or the orchestrator edge cases
  (O1 carve-out, O2 trivial→/dispatch, O3 no-arg, O4 change-of-mind). O5 mirror-diff is
  uncovered but **correctly** so (a maintenance constraint, not a prompt-testable
  promise).
- **Two of the three evals have uncheckable expectations** (eval2/eval3 "launches the
  workflow" + eval3 `finalReportPath`) because the mandatory cost-gate AskUserQuestion
  ends the turn first — a faithful agent scores a false negative there.
- **Highest-value additions:** PE-A (trivial→decline — tests the skill's defining
  boundary), PE-B (carve-out — tests the most dangerous branch), and ENG-1/ENG-2/ENG-6/
  ENG-9 (the engine's core loop, escalation, finalize, and empty-list paths).
