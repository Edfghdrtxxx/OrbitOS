# A4 — Schema / StructuredOutput robustness + cost-control coherence audit

Scope: `orchestrate-inline.workflow.js` (ENGINE) and `SKILL.md`, lens = StructuredOutput
abort-class robustness + cost-control coherence. All findings are NEW (not among the 5
known 2026-06-29 entries). Every finding cites ENGINE line numbers unless noted as SKILL.

Reference incident (must be kept in mind): evolution.md 2026-06-24 — a mandatory
`agent({schema})` return whose model output repeatedly fails schema validation drives the
runtime to "StructuredOutput retry cap (5) exceeded"; `agent()` then THROWS, aborting the
whole workflow and losing downstream stages even though earlier deliverables are on disk.
The documented mitigation = (a) require only `summary`, drop unconsumed required fields,
(b) prompt the agent to return a SHORT plain-text summary and NOT spill arrays/tags into it.

## F1 — The abort-class mitigation was applied to only 2 of the 4 mandatory schemas; VERDICT/CRITIC keep the full strict validation surface (`additionalProperties:false`)

**Verifiable facts.** Four spawn sites pass a mandatory `schema:` (a malformed return at any
of them can throw and abort the run, per 2026-06-24):

- impl → `IMPL_SCHEMA` (line 219): `additionalProperties:true`, `required:['summary']` (lines 70-73).
- verify → `VERDICT_SCHEMA` (line 224): `additionalProperties:false`, `required:['approved','blockers']` (lines 90-93).
- critic → `CRITIC_SCHEMA` (line 308): `additionalProperties:false`, `required:['complete','gaps']`, and the nested gap object is ALSO `additionalProperties:false` with `required:['id','objective','outputPath']` (lines 102-125).
- finalize → `FINAL_SCHEMA` (line 388): `additionalProperties:true`, `required:['shortSummary']` (lines 130-138).

The code comment at lines 66-69 explicitly states IMPL was relaxed to dodge the 2026-06-24
abort; evolution.md line 49 confirms IMPL_SCHEMA/FINAL_SCHEMA were hardened with
`additionalProperties:true` + summary-only required. **VERDICT_SCHEMA and CRITIC_SCHEMA did
not receive the same treatment.**

**Why `additionalProperties:false` matters here (and why it is NOT a misread of the
semantics).** `additionalProperties:false` means the object may contain ONLY the listed
properties; any extra key fails validation. That is a strictly LARGER failure surface than
`additionalProperties:true`. The 2026-06-24 abort is "repeated validation failure → retry
cap → throw." Any repeated validation failure reaches it — a missing required field is the
*documented* trigger, but an unexpected extra key is the *same* trigger by a different door.
A verbose skeptic improvising a top-level `severity`/`recommendations`/`details` key (very
natural for a "find problems" agent) gets rejected by VERDICT_SCHEMA; a critic adding a
nested `priority`/`rationale` key to a gap gets rejected by CRITIC_SCHEMA's nested
`additionalProperties:false`.

**Important nuance (do not over-claim).** For VERDICT_SCHEMA the required fields `approved`
and `blockers` ARE genuinely consumed (line 226 reads `verdict.approved` and
`verdict.blockers`; line 237 feeds `blockers`/`nits` back into `implementPrompt`). So you
CANNOT relax them to summary-only the way IMPL/FINAL were relaxed — they must stay required.
The fix is therefore the OTHER half of the 2026-06-24 mitigation: **flip
`additionalProperties` to `true`** (the consumer only ever reads `.approved`, `.blockers`,
`.nits`, so rejecting extra keys buys nothing and only adds abort surface), and add the
no-spill prompt guard (see F3).

**Fix sketch:**
```js
// VERDICT_SCHEMA / CRITIC_SCHEMA: relax the top-level (and the nested gap object)
//   additionalProperties: false  ->  additionalProperties: true
// Keep required as-is (those fields are consumed). Extra keys are then ignored,
// not rejected — matching the IMPL/FINAL hardening at lines 66-69, evolution.md:49.
```
Severity: medium. The common path (approved=true / complete=true / gaps=[]) is low-risk, but
the contested/gaps path — the exact path that is already under stress — keeps the full strict
surface.

## F2 — Critic gap-items bypass BOTH the same-file backstop AND the dependency scheduler; the schema cannot even express serialization intent

**Verifiable facts.** Gap construction at lines 315-323:
```js
const gapItems = critic.gaps.map((g) => ({
  id: g.id, objective: g.objective, inputContext: g.inputContext || '',
  outputPath: g.outputPath, reviewFocus: g.reviewFocus || '',
  mutatesFiles: g.mutatesFiles === true,   // line 321: defaults FALSE when omitted
  dependsOn: [],                            // line 322: hardcoded empty
}))
const gapResults = await Promise.all(gapItems.map((g) => implementAndVerify(g)))  // line 324
```

Three distinct holes, all schema-rooted:

1. **No same-file serialization.** The `lastWriterOfPath` backstop (lines 53-60) runs ONCE,
   over the original `rawItems` only, at module top. It is never re-run for `gapItems`. Two
   gaps in the same critic round that share an `outputPath` are NOT chained. Because there is
   no worktree (lines 24-28 / SKILL line 26), two gap agents writing the same real file in
   parallel race → lost/corrupted writes.

2. **The scheduler is bypassed entirely.** Gaps call `implementAndVerify(g)` DIRECTLY (line
   324), not `run(g)`. `dependsOn` is consulted ONLY inside `run()` (lines 263-275);
   `implementAndVerify` (line 212) never looks at it. So even the hardcoded `dependsOn:[]` is
   moot — and even if the critic *could* express a dependency, it would be ignored. Gaps run
   in unconditioned full parallel via `Promise.all` (line 324).

3. **`mutatesFiles` silently defaults false (line 321) and the schema makes it optional**
   (`mutatesFiles` is NOT in the gap `required` set, line 113; it is only an optional property
   at line 120). A gap that is actually a mutation, but where the critic omitted
   `mutatesFiles`, is handed the *content-producer* prompt (line 180: "This item is a content
   producer. Write the deliverable to ...") instead of the mutate prompt (line 179). The agent
   is mis-instructed to write a fresh deliverable rather than edit an existing source file —
   and it simultaneously bypasses the same-file backstop. The two failure modes compound.

**Schema angle (my lens, distinct from A1's logic angle).** The CRITIC gap schema (lines
108-124) has NO `dependsOn` field and makes `mutatesFiles` optional. So the critic
*structurally cannot* signal "serialize this gap behind that one" or even reliably signal
"this gap mutates." The schema makes safe gap scheduling impossible by construction, and the
constructor code (lines 321-322) then hardcodes the unsafe defaults.

**Fix sketch:**
```js
// 1. Require mutatesFiles in the gap schema (CRITIC_SCHEMA, line 113):
//      required: ['id', 'objective', 'outputPath', 'mutatesFiles']
//    (or, conservatively, default unknown gaps to mutatesFiles:true).
// 2. Fold gaps into the SAME scheduling structures, then route through run():
for (const g of gapItems) {
  if (g.outputPath && lastWriterOfPath.has(g.outputPath)) {
    const prev = lastWriterOfPath.get(g.outputPath)
    if (prev !== g.id && !g.dependsOn.includes(prev)) g.dependsOn.push(prev)
  }
  if (g.outputPath) lastWriterOfPath.set(g.outputPath, g.id)
  byId.set(g.id, g)
}
const gapResults = await Promise.all(gapItems.map(run))   // run(), not implementAndVerify()
```
Severity: medium-high (silent data race on the real tree, no worktree to catch it).

## F3 — The "SHORT summary / no-spill" guard is MISSING at exactly the two strict-schema returns (verify + critic)

**Verifiable facts.** The guard exists verbatim in two prompts:
- `implementPrompt` line 185: "Call StructuredOutput with a SHORT plain-text `summary` ... Do
  NOT paste file contents or embed XML-ish tags, lists, or arrays INSIDE the summary string —
  that triggers serialization failures that can abort the whole run."
- finalizer prompt line 386: "Return ... a SHORT (2-4 sentence) plain-text `shortSummary`
  ONLY. Do NOT paste the report or embed tags/arrays inside the summary string ..."

It is ABSENT from:
- `verifyPrompt` lines 190-207. The closing instruction (line 205) only says "List blockers
  with file:line where possible; nits separately." No length cap, no no-spill warning.
- the critic prompt lines 297-307. Closing instruction (line 306) only says "return
  complete=false and gaps[] as new work-items." No length cap, no no-spill warning.

**The irony that makes this load-bearing.** The two prompts that LACK the guard
(verify, critic) are precisely the two backed by `additionalProperties:false` schemas with
*required structured fields* (`blockers` array; `gaps` array-of-objects) — i.e. the
highest-spill-risk surface. The two prompts that HAVE the guard (impl, finalize) are the two
already relaxed to `additionalProperties:true` + summary-only. **The protection is applied
exactly backwards from where the abort risk concentrates.**

Concretely, CRITIC is the closest re-instantiation of the 2026-06-24 incident: a *required
structured array of objects*, each with required sub-fields — the same shape as the
`filesWritten` array that triggered the original crash — produced by an agent with no
no-spill guidance. And an abort here is uniquely costly: the critic only runs when everything
already passed (`allApproved(results) && !hitCap`, line 293), so a thrown
retry-cap error propagates past the structural gate and past FINALIZE — destroying a fully
successful run's consolidated report while every per-item deliverable sits completed on disk.
That is the 2026-06-24 loss pattern verbatim.

**Fix sketch:** append the same no-spill clause used at lines 185/386 to `verifyPrompt`
(after line 205) and to the critic prompt (after line 306). For the critic, add: "Put every
gap's detail in its `objective`/`reviewFocus` fields; keep each field short; do NOT embed
nested arrays/tags inside any string field."
Severity: medium-high.

## F4 — Cost-control incoherence: an approved large run can silently hit MAX_AGENTS=60 mid-flight; the cap then (a) shadows the true reason and (b) starves the finalizer, losing the durable report

**Verifiable facts.**
- `MAX_AGENTS = 60` (line 16), `MAX_ROUNDS = 4` (line 17), `CRITIC_ROUNDS = 2` (line 18).
- Each verify round spawns impl + verify = 2 agents (lines 216, 221); a fully contested item
  loops MAX_ROUNDS → up to **8 agents per item**.
- The cost-gate shown to the user (SKILL line 35) is "≈ items × 2, × up to maxRounds on
  contested items, + critic + finalizer" — a *rough* estimate with no reconciliation against
  the 60 backstop, and the user cannot know how many items will turn contested.
- SKILL line 67 calls the Phase-3 cost-gate "the primary cap," but the real hard backstop
  (60) is a fixed constant unrelated to the approved work-list size and is never surfaced at
  gate time.

**Can an approved run silently hit 60? Yes.** With 8 agents per fully-contested item,
MAX_AGENTS=60 guarantees full headroom for only ⌊60/8⌋ = **7 fully-contested items** (before
critic + finalizer consume more). A perfectly legitimate 10-15 item audit (this very audit is
multi-item) that runs into contestation walls into the cap mid-flight. The user approved scope
X; the engine silently enforces a hidden ceiling that may be < worst-case(X).

**What happens when the cap is hit mid-flight (traced from source):**
- `spawn()` returns `null` for all further spawns without incrementing (lines 147-151), so the
  count does not blow past 60 — good.
- But every remaining item's impl AND verify return `null`; `approved` is false (line 226);
  after MAX_ROUNDS the item returns `status:'needs-human'` WITH an `_escalate` whose reason is
  `"verify loop exhausted ${MAX_ROUNDS} rounds without approval"` (lines 239-250).
- **Misleading-reason bug.** The structural gate checks `escalated` BEFORE `hitCap` (lines
  334-347): `if (escalated) needsHuman = escalated._escalate` (lines 337-338). Since the
  cap-starved items all carry `_escalate`, `escalated` is truthy and the operator is told some
  arbitrary item "exhausted 4 rounds without approval" — NOT the true root cause "we ran out
  of agent budget." The cap's own honest message at line 346 is **dead code** in this
  scenario. The operator will chase a phantom contested item.
- **Finalizer-starvation bug (the serious one).** The finalizer is spawned via `spawn()` at
  line 367; once capped it returns `null`. `finalizer` is null → `shortSummary` stays `''`
  (line 390) → the fallback return is used (line 403). Critically, the `_REPORT.md` is written
  ONLY by the finalizer agent (its prompt, lines 380-381). **No finalizer → no report.** Yet
  the return still advertises `finalReportPath` (line 401) pointing at a file that was never
  written, and SKILL Phase 4 (line 48) then instructs the orchestrator to "read
  `finalReportPath`" — which will be missing or stale. So hitting the cost cap *defeats the
  durable-report guarantee* that FINALIZE was added to provide. This is a genuine
  interaction bug between cost-control and the durability feature (not a re-report of the
  feature itself).

**Fix sketch:**
```js
// (a) Reconcile the cap with approved scope — surface the real ceiling at gate time.
//     At launch compute worstCase = items.length * MAX_ROUNDS * 2 + (CRITIC_ROUNDS*?) + 1;
//     if worstCase > MAX_AGENTS, either scale MAX_AGENTS up to it or have the SKILL
//     cost-gate display "hard backstop = 60; this scope's worst case = N" so the user
//     approves against the true ceiling.
// (b) Guarantee the finalizer always runs: reserve a slot (effective work cap =
//     MAX_AGENTS - 1) or spawn the finalizer via agent() directly, bypassing the cap —
//     it is a single bounded necessary agent; without it the run yields no deliverable.
// (c) Fix the shadowed reason: when hitCap, prefer/merge the cap reason so the operator
//     sees "MAX_AGENTS reached mid-flight" instead of a phantom per-item exhaustion.
//     e.g. reorder lines 334-347 to check hitCap first, or annotate _escalate reasons
//     produced after the cap was hit.
```
Severity: high (silently converts approved work into a pile of mislabeled escalations AND
loses the consolidated report — two of the system's headline guarantees at once).

## F5 (bonus) — IMPL_SCHEMA is only HALF-hardened: the nested `changes` item keeps `additionalProperties:false`, reintroducing the abort surface the comment claims to have removed

**Verifiable facts.** The comment at lines 66-69 justifies IMPL_SCHEMA's safety with "required
is summary-only ... so requiring them only risks a StructuredOutput abort." But the
implementer prompt (line 185) explicitly invites the model to "also include `outputPath` and
`changes[]`," and the `changes` array item is defined `additionalProperties:false` with
`required:['file','change']` (lines 77-85).

JSON-Schema validates OPTIONAL-but-PRESENT fields: `required` only governs presence; once a
property appears it is checked against its subschema regardless. So an implementer that
volunteers a slightly-off entry — e.g. `{file:'x.js', change:'did y', line:42}` — fails on the
extra `line` key, or `{file:'x.js'}` fails the `change` requirement. Repeated → retry cap →
abort. `changes` is advisory only (shown to the skeptic at line 202, stored at lines 233/354,
never drives control flow), so this strict nested surface buys nothing while reintroducing
exactly the abort vector the lenient top-level was meant to remove. FINAL_SCHEMA has no such
nested object (lines 130-138) and is genuinely safe; IMPL is the half-hardened outlier.

**Fix sketch:** set the nested `changes` item to `additionalProperties:true` (lines 79-84),
OR drop the `changes[]` invitation from the implementer return instruction (line 185) so the
model is never nudged to emit the strict-validated structure at all.
Severity: low-medium (latent; only bites when the model volunteers a malformed optional
`changes` entry, but it directly contradicts the comment's stated safety rationale).
