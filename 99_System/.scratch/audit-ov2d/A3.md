# A3 — Path Portability & Cross-Repo / Mirror Hazards

Audit of `orchestrate-v2-D-workflow` (SKILL.md + `workflows/orchestrate-inline.workflow.js`).
All findings independently verified this run. Citations are `file:line`. The 5 already-known
findings and the generic "mirror hazard" already in `evolution.md` are NOT re-reported here —
these are NEW, concrete portability breaks plus a fresh independent verification of the two-tree state.

**Run context (verified):**
- Session CWD = `D:/obsidian/OrbitOS` (`pwd` → `/d/obsidian/OrbitOS`).
- Skill under audit lives in a *different* repo: `D:/Something/research/MATE-Automation-V4`.
- Two repos, two git roots → every relative path in the skill is being interpreted this run
  against a repo that is NOT the skill's own.

---

## A3-1 — GENUINE BREAK: launch `scriptPath` is RELATIVE; resolves only when CWD == skill repo root. Broken this very run.

**Evidence.** `SKILL.md:39` (inside the Phase-3 launch snippet):
```
scriptPath: '.claude/skills/orchestrate-v2-D-workflow/workflows/orchestrate-inline.workflow.js',
```
This is a **relative** path (no drive, no leading `/`). A relative `scriptPath` is resolved
against the session CWD.

**Verified failure this run.** CWD is `D:/obsidian/OrbitOS`, so the path resolves to
`D:/obsidian/OrbitOS/.claude/skills/orchestrate-v2-D-workflow/workflows/orchestrate-inline.workflow.js`.
I confirmed that file **does not exist** (existence check returned "DOES NOT EXIST in OrbitOS").
The real script only exists under the skill's own repo root
(`D:/Something/research/MATE-Automation-V4/.claude/skills/...`). So a real Workflow launch issued
this run would hit the engine-unreadable case that `SKILL.md:71` itself names
("If the `Workflow` launch itself fails ... unreadable `scriptPath`").

**Why it's a real break, not a convention.** The path is portable ONLY under the implicit,
undocumented precondition "CWD is the skill's repo root." Nothing in SKILL.md states that
precondition, and the orchestrator is routinely invoked from an unrelated vault (as here). The
engine's own default output path (A3-2) is likewise CWD-relative, which is consistent with
CWD-relative resolution being the operative rule.

**Honest caveat (skeptic-grade).** I did not *execute* the Workflow tool to observe its resolution
base directly — that would be a real background launch, outside this read-only audit's scope. The
three hard facts I verified are: (a) the `scriptPath` string is relative, not absolute;
(b) the literal does not exist under the current CWD; (c) it does exist under the skill's repo root.
If the runtime were to anchor relative `scriptPath` to the skill directory instead of CWD, the
break would not occur — but nothing in SKILL.md or the engine pins resolution to the skill dir.

**Fix direction.** Make `scriptPath` absolute (or anchor it to the skill dir), OR document
"launch only with CWD = skill repo root" as a hard precondition in SKILL.md.

## A3-2 — GENUINE HAZARD: default `finalReportPath` is CWD-relative AND hardcodes the OrbitOS `99_System` vault convention.

**Evidence.** `workflows/orchestrate-inline.workflow.js:41`:
```
const finalReportPath = A.finalReportPath || `99_System/.scratch/${sessionId}/_REPORT.md`
```
The default is **relative** (resolved against CWD) and names `99_System/.scratch` — an
OrbitOS-vault structural convention (defined in OrbitOS `CLAUDE.md`, the `99_System` top-level dir),
not a generic scratch location.

**Why it bites.**
- The durable report lands at `<CWD>/99_System/.scratch/<sessionId>/_REPORT.md` — i.e. in
  whatever repo happens to be CWD, NOT the skill's repo and NOT (by default) the audited artifact's
  repo. This run, with CWD = OrbitOS, the report would be written into the OrbitOS vault while the
  audited skill sits in MATE-Automation-V4 — a silent cross-repo split unless `finalReportPath` is
  explicitly overridden (which this audit does: items write under `.../audit-ov2d/`).
- The finalizer prompt (`...workflow.js:381`) instructs "create parent directories," so when CWD is
  a repo *without* a `99_System`, the engine does not error — it **mints** a `99_System/.scratch`
  tree inside that foreign repo, leaking the OrbitOS vault convention into an unrelated codebase.
- It happens NOT to error in MATE-Automation-V4 only because that repo *also* has a `99_System`
  (verified: `99_System EXISTS in MATE-Automation-V4`). That is coincidence — both repos follow the
  same author's vault layout — not portability.

**Distinguish (not over-claiming).** In-repo, with CWD = the vault/skill root, `99_System/.scratch`
is an acceptable convention. The portability defect is narrow and specific: the *default* is both
(a) CWD-relative and (b) named after an OrbitOS-specific directory, so it is not safe for a generic
CWD. A generic engine should default to an OS temp dir or a skill-relative scratch path, with the
vault convention being the explicit override, not the baked-in default.

## A3-3 — VERIFIED STATE: two REAL copies (not symlinks), NO sync script — lockstep is maintained by hand only.

**Not symlinks (independently verified, per the Windows-reparse-point memory).**
`Get-Item -Force` on both tree roots and both `workflow.js` files returns `Attr=Directory` /
`Attr=Archive` with an **empty `LinkTarget`** — i.e. real files, NOT reparse points/junctions/symlinks.
(Note: OrbitOS `CLAUDE.md` says skills are "symlinked `.agents` → `.claude`"; that describes the
*OrbitOS* vault's setup, and does NOT hold for the MATE-Automation-V4 repo where this skill actually
lives — there they are two independent real copies.)

**No sync/mirror tooling exists (verified).** A repo-wide grep for `agents/skills` / `.claude/skills`
and for any file named `*sync*`/`*mirror*` surfaced only: a LaTeX `main.synctex.gz` (irrelevant) and
unrelated eval transcripts / other skills' SKILL.md. There is **no** script that copies one tree to
the other. This confirms `evolution.md:50`'s "no sync script" as still true.

**Both trees are independently git-tracked** in the MATE repo (`git ls-files` lists both
`.agents/skills/orchestrate-v2-D-workflow/...` and `.claude/skills/orchestrate-v2-D-workflow/...`),
and neither is gitignored. So nothing — not a symlink, not a sync job, not gitignore — prevents the
two copies from diverging; identity is preserved purely by the human editing both by hand.

precisely the surface `evolution.md:50` warned about; the audit confirms the warning is structural,
not yet re-triggered.

## A3-5 — GENUINE HAZARD: the launch hardcodes the `.claude` tree, so only that copy executes; a fix landing in `.agents` only is silently INERT.

**Which copy actually runs.** `SKILL.md:39` hardcodes `.claude/skills/...` in `scriptPath`. Therefore
the engine that executes is the **`.claude`** copy. The `.agents/.../orchestrate-inline.workflow.js`
is never invoked by the documented launch line — it is a dead mirror as far as execution goes (git
tracks it, the runtime ignores it).

**Directionality is non-obvious and unguarded.** `evolution.md:50` warns `.agents` is "not necessarily
source-of-truth" and that a blind `.agents → .claude` mirror once clobbered a newer `.claude` edit.
Combined with A3-3 (no sync) and the hardcode above:
- A fix that lands in **`.agents` only** → **inert**: the running engine (`.claude`) keeps the old
  behavior. The author may believe the bug is fixed while production still runs the unpatched code.
- A fix that lands in **`.claude` only** → live, but the git-canonical-looking `.agents` tree goes
  stale, and a later "resync from `.agents`" would silently revert the fix.

There is no guard, assertion, or check that the executing (`.claude`) copy matches the
authoring (`.agents`) copy. This is a NEW, concrete consequence of the relative+hardcoded paths,
distinct from the generic "mirror hazard" note already in evolution.

## A3-6 — SECONDARY (cross-cutting with the mirror): pending deletions must be applied to BOTH trees, and one removal is undocumented.

Lower-severity, noted for completeness since it intersects "what happens if a change lands in only one tree":
- The removed-mode cleanup (`evolution.md:43`) is on disk in both trees (the four `D` files are
  ABSENT from both working trees) but the **deletions are uncommitted in both** (A3-4). Until
  committed in both, a checkout/clone resurrects `references/*.md` and `orchestrate-spec.workflow.js`,
  and a single-tree commit would leave the mirror inconsistent.
- `references/inline-mode.md` is also deleted (git `D`) but `evolution.md:43` only documents removing
  `spec-mode.md`, `task-file-format.md`, and `orchestrate-spec.workflow.js`. Minor doc gap; flagged
  so the mirror/commit step doesn't treat it as accidental.

## Bottom line

- **Two genuine portability BREAKS:** (A3-1) relative `scriptPath` — verified non-existent under this
  run's CWD; (A3-2) CWD-relative + OrbitOS-specific default `finalReportPath`.
- **Two genuine cross-repo HAZARDS:** (A3-3) real (non-symlink) duplicated trees with no sync tooling;
  (A3-5) only the hardcoded `.claude` copy executes, so a one-tree fix can be silently inert.
- **Verification of state:** (A3-4) the two trees are byte-identical and in git lockstep *right now* —
  drift is latent, not currently present; parity is hand-maintained.
- **Acceptable conventions (NOT flagged as breaks):** `99_System/.scratch` *as an override* when CWD is
  the vault root; tracking both trees in git. The defect is only when these become the relative,
  hardcoded *defaults* of a skill that is launched from an arbitrary CWD in a different repo.
