## A6-1 — "The engine concurrency cap" does not exist: fan-out is unbounded `Promise.all`; the only ceiling is the cumulative-count `MAX_AGENTS`, not a concurrency throttle. **SKILL↔ENGINE inconsistency + cost-coherence defect**

**SKILL side (the claim).**
- SKILL.md:67 lists "**the engine concurrency cap**" as a distinct engine-internal mechanism, set apart by commas
  from `MAX_ROUNDS` and `MAX_AGENTS` — i.e., presented as a *third*, separate cap, not a restatement of `MAX_AGENTS`.
- The engine's own scheduler comment reinforces it: engine:255-256 —
  `// Dependency-aware scheduler: independent items run in parallel (concurrency` /
  `// capped by the engine), dependent items wait.` This explicitly asserts the engine throttles concurrency.

**ENGINE side (the reality).** There is no semaphore, pool, `p-limit`, batch window, or in-flight counter anywhere
(grep above: zero matches for all of them). Fan-out is bare, fully-parallel `Promise.all` over a `.map`:
- engine:284 — `let results = await Promise.all(items.map(run))` — every independent (no-`dependsOn`) top-level item
  starts its implementer in the same tick.
- engine:324 — `const gapResults = await Promise.all(gapItems.map((g) => implementAndVerify(g)))` — every
  completeness-critic gap item fans out fully in parallel too.
- engine:264 — `const depResults = await Promise.all(deps.map(run))` — dependency resolution is likewise unthrottled.

The ONLY ceiling on agent creation is the cumulative-count backstop in `spawn()`, engine:146-154:
```
async function spawn(prompt, opts) {
  if (agentCount >= MAX_AGENTS) { ... return null }   // 147-151
  agentCount++                                         // 152
  return agent(prompt, opts)                           // 153
}
```
`agentCount` is a **monotonically increasing total**, never decremented when an agent finishes. So `spawn` enforces
a *lifetime quota* ("no more than 60 agents will ever be created this run"), which is categorically different from a
*concurrency cap* ("no more than K agents run at once"). With, say, 40 independent items, engine:284 calls `spawn`
40 times in one tick → up to ~40 implementers genuinely in flight simultaneously; with ≥60 independent items the
first ~`MAX_AGENTS` (engine:16, `= 60`) fire concurrently before `spawn` starts returning `null`. Peak instantaneous
concurrency is bounded only by the independent-item count, itself only ceilinged by the lifetime quota — there is no
per-instant throttle of any kind.

**Why this is a defect, not a nitpick.**
1. *SKILL↔ENGINE inconsistency:* SKILL.md:67 and the engine:255-256 comment both assert a concurrency cap that the
   408-line engine never implements. A maintainer reading "concurrency capped by the engine" would reasonably assume
   a fan-out width limit exists and (e.g.) size a downstream rate-limited resource against it; there is none.
2. *Cost-control-coherence defect:* the section is titled "Cost control (**hard caps**)". A concurrency cap is
   precisely the lever that bounds *peak simultaneous* spend/load. Its absence means the only real ceiling is the
   lifetime quota — so the section advertises a hard cap it does not possess, against a header that promises hard caps.

## A6-2 — The `budget` / `+Nk` cap does not exist: `budget` is read/enforced nowhere and `+Nk` is parsed nowhere — it lives only in two comments. **SKILL↔ENGINE inconsistency + cost-coherence defect**

**SKILL side (the claim).** SKILL.md:67 closes the cost-control section with:
> "`budget` is only an extra cap (null unless the user set `+Nk`)."
This tells the reader (a) an engine-honored `budget` cap exists, and (b) a user can raise/set it with a `+Nk`
argument.

**ENGINE side (the reality).**
- `budget` appears on exactly **one** line, the header comment engine:14 —
  `// backstops; \`budget\` is only an extra cap and is null unless the user set +Nk.` — and **nowhere else**.
- The args normalizer reads only `sessionId`, `objective`, `items`, `finalReportPath` (engine:36-41):
  ```
  const sessionId = A.sessionId || 'inline'
  const objective = A.objective || '(overall objective not provided)'
  const rawItems = Array.isArray(A.items) ? A.items : []
  const finalReportPath = A.finalReportPath || `99_System/.scratch/${sessionId}/_REPORT.md`
  ```
  There is **no `A.budget`** read (grep: zero matches) — the value the comment calls a cap is never even ingested.
- `+Nk` appears only inside that same engine:14 comment; there is **no parsing** of a `+Nk` token anywhere (grep:
  the only `Nk` match is engine:14). No code path can ever make `budget` non-null.
- Consequently `budget` is enforced on **zero** spawn decisions: the verify loop (engine:215 `for ... round <=
  MAX_ROUNDS`), the critic loop (engine:295 `for ... critRound <= CRITIC_ROUNDS`), and the `spawn` gate
  (engine:147 `agentCount >= MAX_AGENTS`) are governed solely by the two real constants `MAX_ROUNDS`/`MAX_AGENTS`.

**Why this is a defect.**
1. *SKILL↔ENGINE inconsistency:* SKILL.md:67 documents a user-tunable `+Nk` budget cap as a real (if optional)
   control surface. A user who passes `+Nk` (or a `budget` value) expecting a tighter spend ceiling gets **silent
   no-op**: the arg is dropped at engine:36-41 and the run proceeds under the fixed `MAX_AGENTS=60` lifetime quota.
   This is worse than a missing feature — it is a documented control that fails silently.
2. *Cost-control-coherence defect:* a "budget" is the canonical cost-control primitive. The section's claim that an
   extra spend cap is available ("only an extra cap") describes a guarantee the engine cannot honor, again under a
   header that says "hard caps."

## Honest skeptic-grade caveat (required)

I verified the engine **source**; I did not (and from this read-only audit cannot) inspect the Workflow RUNTIME that
injects the `agent()` global at engine:153. It is entirely possible the runtime imposes its own internal concurrency
limit or a global agent budget on `agent()` calls — many such harnesses do. **That possibility does not rescue the
claim**, for two reasons:
- SKILL.md:67 and engine:255-256 both attribute the cap to **"the engine"** specifically, and the engine code
  contains no such throttle. If a limit exists, it belongs to the runtime, and the documentation mislocates it —
  still an inaccuracy, and one a maintainer editing *the engine* would be actively misled by.
- For `budget`/`+Nk` there is no runtime-rescue argument at all: the engine never reads `A.budget` and never parses
  `+Nk` (engine:36-41), so even a budget-aware runtime is never handed the value the SKILL says the user can set.

So both are stated as: **the named cap is absent from the engine that the SKILL says owns it.** I do not assert the
runtime is unthrottled — only that the engine, where SKILL.md:67 and the engine:255-256 comment place the cap, is.

## Bottom line

Of the four engine-side caps named in SKILL.md:67, two are phantom: "the engine concurrency cap" (no
semaphore/pool/p-limit/throttle; fan-out is unbounded `Promise.all` at engine:284/324/264; the only ceiling is the
cumulative-count `MAX_AGENTS` quota at engine:147-152, which is not a concurrency cap) and the `budget`/`+Nk` cap
(`budget` read nowhere, no `A.budget` at engine:36-41, `+Nk` parsed nowhere — both live solely in the comment at
engine:14). Each is simultaneously a SKILL↔ENGINE documentation inconsistency and a cost-control-coherence defect
under a section titled "hard caps." Skeptic caveat honored: the runtime `agent()` may throttle, but the SKILL/engine
attribute the caps to the engine, whose code contains neither.
